# Roadmap

Thin by design, per [project-principles](../design/project-principles.md): sequence and intent only. Each slice gets a
just-in-time plan in `docs/plans` when it starts (small enough to implement and verify in one session) and is archived
when implemented. Slice boundaries follow data availability; never more than one slice is planned in detail.

Slices 0–2 have landed — the read CLI, genre handling, and the claim registry all extended slice 2's source layer. The
path source is next: the second source arrives before MusicBrainz, a cheap local analyzer to switch on merging gently
(ADR 0008), and slices 3–6 walk it from the merge seam to the facts only a filename carries.

## Slices

00. **CLI skeleton — `leek`.** The first runnable surface: the `leek` entry point wired through `[project.scripts]`. A
    bare `leek` greets with an about card; `version` and `help` are the first verbs (ADR 0003). Data-backed commands
    arrive with the slices that have data behind them.

01. **Library core — `leek add`.** Music enters the database. The merged-view core tables and the source-layer write
    path (file tags as the only source, identity merge — layering from day one, machinery deferred). Tag reading via
    mediafile, copy-on-import, Alembic from the first migration. Makes TrackInfo/AlbumInfo real.

02. **Visibility — `leek list` and `leek info`.** The library becomes queryable and dogfoodable before anything clever.
    `info` exposes the source layer, not just the merged view. `list` shipped with bare substring terms as the floor
    (ADR 0011); the query language is beets-inspired by decision (ADR 0012), but its grammar is designed when a real
    query demands it, not ahead of contact.

03. **Path source — the seam, on the year.** The cheapest second source switches on the merge machinery, as gently as
    possible (ADR 0008). `sources` gains a priority and `merge()` resolves the highest-priority claim per scalar field
    instead of copying the lone one; path claims carry confidence (recorded, not yet decisive — the punt). The parser
    does one near-unambiguous thing: read the parenthesised `(2001)` year, so a year-less file set takes its year from
    the folder. This slice is about the merge seam, not the parser.

04. **Path source — the grammar (harness-first).** The real parser: `Artist - Album (Year) [FLAC] {Label - CAT#}` and
    the real-world variants. Risk leads with verification, so the fixture harness — directory names to expected parse
    and confidence — is built first, the shape the matcher harness will reuse. Title joins year in the priority-merge.

05. **Path source — relational merge.** artist, then genre: a foreign-key and a junction field merge by reconciling
    rows, not by picking a winning string — the open problem the glossary flags. The design-heavy slice; may swap with
    slice 6.

06. **Path source — path-only facts.** format, region, catalogue number: release facts file tags never carry. Conflict
    free (only the path asserts them), so no resolution to design — the work is new claim fields and whether each earns
    a merged column. Bankable; may precede slice 5.

07. **The feat analyzer — `ftintitle`.** The second analyzer: relocate a raw "feat. X" out of the artist credit and into
    the title. Narrower than the path source, but its claim contradicts file_tags on the same fields — merge's first
    disagreement-with-itself, taken on once the path source has proved the clean case.

08. **Matcher parity harness.** The riskiest work gets its verifier first: fixture inputs with beets' known matching
    outputs, which the port must reproduce. No porting in this slice.

09. **The matcher port and MusicBrainz — `leek match`.** The networked source arrives, and with it the entities its data
    populates (release groups, recordings, works) and recorded matches with confidence. Ported against the harness,
    never ahead of it.

10. **Merge review queue — `leek review`.** Basic priority-merge already landed with the path source; here the
    pending-changes queue earns its keep at scale — an automated source proposing hundreds of edits is the expected
    case, not the edge: filter by source, accept and reject in bulk, auto-accept rules.

## Later

Not planned in detail; build when needed. `leek init` (creates the library location and the config that retires the
hardcoded `~/Music/leeks` root; config includes a path-rendering style — named styles like `human` / `dashed` / `slug`,
default `human`, deliberately an enum and not a template language; ADR 0010's scheme is the structure, the style only
renders its components, and changing style simply makes paths stale for `leek organize` to re-derive), `leek organize`
(re-derives stale paths per ADR 0010; beets' `move`), tag write-back as its own verb (beets' `write` — it mutates audio
files), artist aliases (the correction machinery for first-seen spellings and diacritic variants), `leek import` (the
full pipeline), further sources (Discogs, RED), background re-polling, the beets migration tool, attachments, format
variants and relationships, listening history, the dump (`leek dump | leek load`: the library as deterministic portable
text — claims and history, never the merged view; the backup format and the engine-migration path, per
[portability](../design/portability.md)), the wantlist (releases with zero files are valid library entries — a wantlist
is a query, not a feature).
