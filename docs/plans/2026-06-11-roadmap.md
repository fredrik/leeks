# Roadmap

Thin by design, per [project-principles](../design/project-principles.md): sequence and intent only. Each slice gets a
just-in-time plan in `docs/plans` when it starts (small enough to implement and verify in one session) and is archived
when implemented. Slice boundaries follow data availability; never more than one slice is planned in detail.

## Slices

0. **CLI skeleton — `leek`.** The first runnable surface: the `leek` entry point wired through `[project.scripts]`. A
   bare `leek` greets with an about card; `version` and `help` are the first verbs (ADR 0003). Data-backed commands
   arrive with the slices that have data behind them.

1. **Library core — `leek add`.** Music enters the database. The merged-view core tables and the source-layer write path
   (file tags as the only source, identity merge — layering from day one, machinery deferred). Tag reading via
   mediafile, copy-on-import, Alembic from the first migration. Makes TrackInfo/AlbumInfo real.

2. **Visibility — `leek list` and `leek info`.** The library becomes queryable and dogfoodable before anything clever.
   `info` exposes the source layer, not just the merged view. `list` shipped with bare substring terms as the floor (ADR
   0011); the query language is beets-inspired by decision (ADR 0012), but its grammar is designed when a real query
   demands it, not ahead of contact.

3. **Matcher parity harness.** The riskiest work gets its verifier first: fixture inputs with beets' known matching
   outputs, which the port must reproduce. No porting in this slice.

4. **The matcher port and MusicBrainz — `leek match`.** The second source arrives, and with it the entities its data
   populates (release groups, recordings, works) and recorded matches with confidence. Ported against the harness, never
   ahead of it.

5. **Merge machinery and review — `leek review`.** With two sources real, merging earns its keep: merge strategies, the
   pending-changes queue, accept/reject, auto-accept rules. The queue must scale to bulk from the start — an automated
   source proposing hundreds of edits is the expected case, not the edge: filter by source, accept and reject in bulk.

## Later

Not planned in detail; build when needed. `leek init` (creates the library location and the config that retires the
hardcoded `~/Music/leeks` root; config includes a path-rendering style — named styles like `human` / `dashed` / `slug`,
default `human`, deliberately an enum and not a template language; ADR 0010's scheme is the structure, the style only
renders its components, and changing style simply makes paths stale for `leek organize` to re-derive), the path source
(directory names as analyzer claims, ADR 0008 — a cheap local second source that could precede MusicBrainz to exercise
merging gently), `leek organize` (re-derives stale paths per ADR 0010; beets' `move`), tag write-back as its own verb
(beets' `write` — it mutates audio files), artist aliases (the correction machinery for first-seen spellings and
diacritic variants), `leek import` (the full pipeline), further sources (Discogs, RED), background re-polling, the beets
migration tool, attachments, format variants and relationships, listening history, the dump (`leek dump | leek load`:
the library as deterministic portable text — claims and history, never the merged view; the backup format and the
engine-migration path, per [portability](../design/portability.md)), the wantlist (releases with zero files are valid
library entries — a wantlist is a query, not a feature).
